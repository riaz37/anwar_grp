## What was found and fixed today (needs independent re-verification)

### 1. CRITICAL — unauthenticated portfolio data leak (fixed)
`app/(dashboard)/projects/page.tsx` was the only dashboard page missing its
own `if (!session) redirect("/login")` guard. A request with no cookie, or
a forged/expired `tf_session` cookie, got HTTP 200 with the full real
portfolio (all project names, owners, health, business units) baked into
the HTML. Every sibling page (`/home`, `/my-work`, `/dashboard`,
`/projects/new`, `/projects/[id]`) already had this guard and was safe.

Fix: added the missing guard (one line). Also added `proxy.ts`
(Next 16's renamed `middleware.ts`) as defense-in-depth — a fast
cookie-presence check that 307-redirects before any rendering for the
no-cookie case specifically (this alone does NOT validate the session,
just checks the cookie exists — the real fix is the per-page DB-backed
check).

**Re-verify:** for every route under `(dashboard)` — no cookie should 307,
a bogus/expired `tf_session` cookie should render a safe empty/redirect
shell with zero project data in the HTML. Test with raw curl, not just a
browser (a logged-in browser's client router masks this).

### 2. CRITICAL — UAT self-approval bypass (fixed)
Any Developer or AI Analyst could toggle the "Business approval received"
stage-gate checklist item (the only record that the Business Owner
actually approved UAT) and then transition the project straight to
Deployment, cutting the Business Owner out entirely.

Fix: `app/api/v1/projects/[id]/checklist/[itemId]/route.ts` now requires
`BUSINESS_OWNER` or `AI_TEAM_LEAD` specifically for that one checklist
label, on top of the existing broader `TOGGLE_CHECKLIST_ITEM` permission.

**Re-verify:** log in as Developer and Analyst, attempt to check that
specific item on a project in `BUSINESS_TESTING_UAT` stage — must 403.
Business Owner and Team Lead must still succeed.

### 3. HIGH — resource-reassignment bypass (fixed)
Any AI Analyst could reassign a project's owner/analyst/developer via
`PATCH /api/v1/projects/[id]`, even though `ASSIGN_RESOURCES` is documented
(and unit-tested in `test/unit/project-permissions.test.ts`) as
`AI_TEAM_LEAD`-only. The route was checking the wrong permission
(`EDIT_REQUIREMENTS`, which includes AI_ANALYST) for people-field changes.

Fix: `app/api/v1/projects/[id]/route.ts` PATCH now splits the check —
`ASSIGN_RESOURCES` for owner/analyst/developer fields, `EDIT_REQUIREMENTS`
for content fields (name/businessProblem/expectedOutcome/date) — checked
independently so a mixed payload can't use the weaker permission to slip
past the stronger one. `components/projects/detail/ProjectRail.tsx`'s UI
gate updated to match.

**Re-verify:** as Analyst, attempt `PATCH` with `ownerId`/`analystId`/
`developerId` → must 403. Attempt with only content fields → must succeed.
As Team Lead, both must succeed.

### 4. HIGH — no participant scoping on project reads/writes (fixed, largest change)
Before today, ANY authenticated user — any role — could read and act on
EVERY project via the API (`GET /api/v1/projects` had no filtering beyond
optional query params; every sub-resource route only checked
`requireAuth()` + coarse role permission, never "is this user actually on
this project"). This contradicted the assignment's own role table
("Developer: View assigned projects" vs. "AI_TEAM_LEAD: View all
projects") and contradicted the marketing page's own claimed behavior.
`isProjectParticipant()` in `lib/project-authz.ts` existed for exactly
this purpose but was never wired into anything except document downloads.

Fix — added `requireProjectParticipant(user, projectId)` to
`lib/project-authz.ts` (throws 404, not 403, so a non-participant can't
distinguish "doesn't exist" from "exists but you can't see it") and a
`PORTFOLIO_WIDE_ROLES` set (`AI_TEAM_LEAD`, `MANAGEMENT`) to
`lib/project-permissions.ts`. Wired into:
- `app/api/v1/projects/route.ts` GET (list) — `where` clause now scopes by
  participant unless role is portfolio-wide.
- `app/api/v1/projects/[id]/route.ts` GET + PATCH (content-field branch).
- `app/api/v1/projects/[id]/{checklist,milestones,tasks,blockers,
  scope-changes,stage-history}/**/route.ts` — every GET and every mutating
  route (11 files total).
- `app/(dashboard)/projects/page.tsx` (portfolio list page) and
  `app/(dashboard)/projects/[id]/page.tsx` (detail page) — same scoping,
  page-side (404 via `notFound()` for a non-participant).

**This is the highest-risk change from today and needs the most thorough
re-verification** — it touched 13 files. Specifically check:
- Every role can still fully do everything on THEIR OWN projects (create,
  transition stage, toggle checklist, add/edit milestones, tasks,

- Non-participant Analyst/Developer/Business-Owner get 404 (not 403, not
  500) on every one of those same operations against a project they're
  NOT on.
- AI_TEAM_LEAD and MANAGEMENT are unaffected (full access) everywhere.
- Business Owner's department-based access (sees projects in their
  department even if not directly assigned) still works — this is a
  distinct rule inside `isProjectParticipant`, easy to regress.
- The project detail PAGE (not just the API) actually 404s cleanly for a
  non-participant, with no data flashing before the 404 (check via curl,
  not just a JS-hydrated browser).
- Nothing that legitimately needs cross-project data broke (e.g. Home,
  My Work, Management Dashboard aggregate across all projects for
  Team Lead/Management by design — these were NOT touched today, but
  confirm they still work now that the underlying project list route has

- Marketing page copy at two spots (`app/(marketing)/page.tsx`, search

## Known, accepted, NOT fixed

- **Cosmetic-only**: React dev console warning "Select is changing from
  uncontrolled to controlled" on `ProjectCreateForm.tsx`'s dropdowns
  (business unit / department / owner). Root cause is
  `components/ui/Field.tsx`'s `SelectField` mapping an empty-string
  initial value to `undefined` for Radix's `<Select>`, then switching to a
  real string once selected — Radix requires this exact pattern (empty
  string is not a valid Radix Select value) so eliminating the warning
  needs a broader form-state refactor across every consumer of
  `SelectField`. Zero functional impact — dev-mode-only, doesn't affect
  submitted values or production behavior. Left as-is; flag to the user
  again if this session has time budget to properly fix it, otherwise
  leave alone rather than half-fixing one form and not the others.
